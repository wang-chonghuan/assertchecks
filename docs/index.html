How to use it

People define correct and agents write the code

assertchecks/e2e.json

{ "id": "E2E-001", "title": "Sign in with a saved account", "status": "active", "run": "regular", "given": ["A registered account"], "when": ["Sign in through the login page"], "then": [{ "id": "A1", "expect": "The dashboard greets the account holder" }] }

tests/E2E-001.spec.ts

test('E2E-001: Sign in with a saved account', async ({ page }) => { // Given / When ... await test.step('Then A1: the dashboard greets the account holder', async () => { await expect(page.getByRole('heading', { level: 1 })).toContainText('Welcome') }) })

Expectations come from the case. They are never copied from what the product shows today.

How to use it

CI runs your cases on a schedule

# .github/workflows/assertchecks-dev.yml on: schedule: - cron: "0 3 * * *" workflow_dispatch: jobs: … steps: - name: Report to AssertChecks if: ${{ always() }} env: ASSERTCHECKS_PING_TOKEN: ${{ secrets.ASSERTCHECKS_PING_TOKEN }}
  • 1cap0 writes this workflow for you
  • 2Store the check's ping token as a CI secret
  • 3A missed schedule turns the check Late

How to use it

Your agent turns failures into tickets

# Sign in once as yourself. Approve in the browser. $ node assertchecks.mjs login # The failures of the latest full run and their ticket status $ node assertchecks.mjs bugs --check dev # Link the ticket you filed back to the cases $ node assertchecks.mjs link --cases E2E-103 \ --ticket https://linear.app/…/ENG-…

Or ask for it in one line

assertchecks cap7 for DEV

  • 1Reads the bugs of the latest run
  • 2Files tickets in your own tracker and workflow
  • 3Links them back so the page shows who is on it

Ping tokens only report runs. People and their agents read and link as themselves.
