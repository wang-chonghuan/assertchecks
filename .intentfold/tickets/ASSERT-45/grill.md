# ASSERT-45 grill

没有问题达到需要问人的门槛：规则是 owner 在 Request 里同意的简化版，其余细节可逆，也能从代码和已有记录判断。以下由 agent 决定。

## Decided for you

1. **“我批准”在通用技能里指谁。** 决定：项目 `system-design.md` 写明的“用例负责人”；没写就停下询问。依据：开发的会话里 human 就是开发本人，owner 要求技能不绑定单个项目，而项目事实都归 `system-design.md`。
2. **“case 描述”包括哪些字段。** 决定：`title`、`given`、`when`、`then`。依据：这些写的是产品该怎样；`data` 是 owner 说开发可自定的数据。
3. **降级或删除算不算。** 决定：删除用例或改 `status`、`run` 也要负责人批准。依据：它们和改 Then 一样能把红用例藏起来；cap2 已禁止为变绿而降级。
4. **什么算批准。** 决定：负责人本人在工单或 PR 上的评论或审查；会话里的人只有 Git 或工单系统身份就是负责人时才算。开发转述不算。依据：Request 的“必须我批准”；身份能查证，口头说法不能。
5. **修产品代码时两次运行在哪跑。** 决定：项目的 local 目标，或已经部署了修复的环境，并确认版本。依据：跑的版本不含修复就证明不了修复。
6. **新红找谁。** 决定：cap7 的分配规则不变；接单的人对照两次运行的变化，确认是某个改动引起的，就交给作者修或回滚。依据：cap7 禁止凭历史猜负责人，先有证据再找人。
7. **共享数据例外里新红如何归因。** 决定：撤销后重跑那条，恢复就是这次改动引起，要换办法；仍然红就不是它引起，可以重新应用，交给 cap7。依据：DEV 上最近有时红时绿的用例，不能一见新红就算到这次改动头上。
8. **脚本修改如何防放水。** 决定：每条改过脚本的用例跑一次 cap5（只读）。依据：owner 已同意“审查时确认脚本还在检查 Then 的每一句”，cap2 也要求改动后用 cap5 审计，不需要新机制。
9. **验收方式。** 决定：照 ASSERT-39，用新 agent 在临时仓库做纸面演练。依据：真实运行要写共享 DEV，而这张单只改技能文本。
