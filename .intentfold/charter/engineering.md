# Engineering

Human-authored architecture and development rules. This file defines how the product is built, how
code changes are made, and how they land. Section shape is fixed by `.intentfold/readme.md`.

The dependency inventory belongs to the lockfile; generated structure belongs to its generator.
Record here only decisions, boundaries, and commands that the repository cannot explain by itself.

*Seeded by IntentFold cap1 on 2026-10-17 from repository evidence; brought up to date with the
repository at the owner's request in ASSERT-12 (2026-10-19).*

## Contract

**Stack**

- TanStack Start (React 19, Vite, Nitro node output) in one process that serves both the pages and
  the push API. TypeScript strict.
- PostgreSQL through the `postgres` driver with parameterized SQL; no ORM.
- Ant Design 6 core components as the only UI system (see `ui.md`).
- pnpm with the committed `pnpm-lock.yaml`; Node 24.

**Structure**

- `src/start.ts` — request middleware: Clerk, and TanStack Start's CSRF check for server functions.
- `src/routes/` — the public homepage (`index`) and `privacy`, `login` (Clerk sign-in), the signed-in pages
  (`_app/...`) and the push API server routes (`api/ping/$token/start`, `report`, and the dry run
  `check`).
- `src/server/` — server-only code: `db` (pool), `session` (the signed-in Clerk user's verified email
  mapped to its CLI-created user), `crypto` (token hashing), `schema` (report-format validation), `judge` and `status` (pure run
  judgement and check-state derivation), `catalog-changes` (pure comparison of two full runs'
  catalogs), `ingest` (push API writes and the dry run), `queries` (membership-scoped reads), `fns`
  (server functions used by routes).
- `src/components/`, `src/lib/` — shared UI, view models (`types`) and the connection guide
  (`connect-guide`) that both the homepage and "Copy for your agent" render.
- `public/schemas/` — the published catalog and result formats; `public/client/assertchecks.mjs` — the
  zero-dependency client projects download on every run.
- `db/migrations/` — numbered SQL migrations applied by `scripts/migrate.ts`.
- `scripts/admin.ts` — the operator CLI; users, memberships, projects and checks are managed only here.
- `tests/` — Node test runner unit tests for pure logic.

**Key decisions**

- Push model for tests: projects call the API; AssertChecks never executes tests.
- Read model for production errors: AssertChecks queries each project environment's own Azure Log
  Analytics workspace with KQL, read-only, as its own Azure identity — the Container App's
  system-assigned managed identity in production, the developer's `az login` locally. No key,
  secret or connection string for a project's telemetry exists in AssertChecks, its database, its
  environment or the repository; the database holds only the workspace reference. Raw error events
  stay in the project's telemetry; AssertChecks stores only the problems it derives from them and a
  person's decisions on those problems.
- The report format is fixed. `public/schemas/*.json` is its single definition: the server validates
  against those files, the site serves them unchanged, and the homepage and client point to them.
- The homepage and the privacy page are public and show no project data; everything else requires
  signing in.
- Identity comes from Clerk (application `assertchecks`: email verification code or Google; production
  Google uses the owner's OAuth client in Google Cloud project `assertchecks-auth`). Access comes
  only from users and memberships created with the CLI, matched by the verified email; an email the
  CLI never added can sign in but sees no project.
- Check state is derived on read; no stored status table.
- Every read is scoped by the signed-in user's memberships; a miss is a 404.
- Ping tokens are stored only as hashes; passwords and sessions are not stored (Clerk holds sessions).
- One database: the easy-app PostgreSQL schema serves production and local development alike, so
  migrations are additive only (add tables or nullable columns; drop/rename only in a later
  migration after the new code is deployed).
- Reports with credential-like content are rejected whole, never cleaned and stored.

## Tools

**Mechanical defence**

```bash
pnpm typecheck && pnpm test && pnpm build
```

**Architecture and generation**

- `src/routeTree.gen.ts` is generated by the TanStack router plugin (`pnpm generate-routes`).
- `pnpm antd-css` pre-renders the Ant stylesheet, git-ignored: `src/generated/antd.dev.css` for
  development and, with `NODE_ENV=production` (as `pnpm build` runs it), `src/generated/antd.css`.
  `vite.config.ts` resolves `#antd-css` to the file for its mode, because Ant prefixes class hashes
  differently in the two modes.
- Migrations: `pnpm migrate` applies `db/migrations/*.sql` in name order once each.

**Dependencies**

```bash
pnpm install --frozen-lockfile
```

**Landing changes**

Feature branches and pull requests to `main` on `wang-chonghuan/assertchecks`. There are no required
CI checks; the mechanical defence above is run before handoff.

```bash
git push -u origin <ticket-branch>
gh pr create --repo wang-chonghuan/assertchecks --base main --head <ticket-branch> \
  --title '<ticket-id>' --body 'Verified IntentFold delivery; see the committed handoff.'
gh pr merge <pr-number> --repo wang-chonghuan/assertchecks --merge
```

## Guidance

**No gratuitous dependencies.** If the existing stack can meet the requirement, do not add, remove,
or change a library. A dependency change is admissible only when the stack genuinely cannot meet the
requirement and the ticket records the human's decision.

**Reuse before inventing.** Existing helpers, config paths, schemas, components, and sources of truth
come first. A second way to do something that already has a way is a defect.

**Respect ownership boundaries.** Put behavior in the module that owns it. Do not reach through a
public interface into another module's private implementation for convenience.

**No fake progress.** No TEMP markers, degradation branches, or mocks standing in for a failed
external dependency. A failed premise is a stop and a report.

**Surgical changes.** Touch what the ticket needs. Do not reformat unrelated files or fold adjacent
cleanup into the same change.

**Uncertainty surfaces.** Ask rather than invent a fallback, compatibility layer, data meaning, or
cross-module contract.

**Complexity hotspots**

- Run judgement (`src/server/judge.ts`) is the product's core promise: never turn missing,
  skipped, unparsed or unrecorded into passed. Change it with unit tests for each outcome.
- Antd styles under SSR: the pre-rendered stylesheet and the fixed `cssVar.key` in `src/theme.ts`
  must stay aligned, or pages flash unstyled before hydration.
- The push API contract is used by other repositories; change it compatibly and, in the same change,
  update `public/schemas/`, the README and `src/lib/connect-guide.ts`.

## Redlines

1. **Committing credentials, tokens, connection strings, or hidden account data** — forbidden
   outright, including source, fixtures, ticket artifacts, and commits. The repository is public.
2. **Discarding or reverting a change already present in a dirty worktree** — forbidden outright.
3. **Adding, removing, or changing a dependency** — not without the human's explicit approval and a
   ticket carrying that decision.
4. **A migration that drops or renames a table or column in the same change that stops using it** —
   forbidden outright.
5. **Hand-editing `src/routeTree.gen.ts` or `src/generated/`** — forbidden outright.
6. **Reading or writing data outside the signed-in user's memberships in `src/server/queries.ts`** —
   forbidden outright.
